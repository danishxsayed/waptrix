# Project Context: Waptrix

## Overview
Waptrix is a professional SaaS platform for WhatsApp Bulk Messaging, built with a modern web stack, integrated with Meta's WhatsApp Business API, and maintained for high reliability.

## Tech Stack
- **Framework**: Next.js 15 (App Router)
- **Language**: TypeScript
- **Styling**: Tailwind CSS & Vanilla CSS (with support for Dark and Light modes)
- **Database/Auth**: Supabase (PostgreSQL)
- **API Integration**: Meta WhatsApp Business API v22.0, Resend (Email)
- **Deployment**: Vercel
- **State Management**: React Hooks, Context API (TenantContext), & Server Components

## Core Architecture
- **(dashboard)**: Grouped route containing all authenticated user pages (Analytics, Connect, Campaigns, Contacts, etc.).
- **TenantContext**: Shared client-side state for authenticated user profiles and messaging quotas. It queries `/api/me` on load to expose the user's role (`owner` | `admin` | `agent`), effective tenant, and staff status context-wide.
- **Middleware**: Handles authentication redirects via Supabase SSR, with explicit exclusions for public routes (login, signup, terms, privacy, password recovery, `/accept-invite`, `/api/auth/` endpoint routes, `/api/webhooks/`, `/api/team/invite`, and `/api/team/create-account`).
- **Client/Server Libs**: Unified Supabase clients in `src/lib/supabase`, Meta API helpers in `src/lib/meta.ts`, and Resend email utilities in `src/lib/email`.
- **API Authentication & RLS Bypass Standard**: Database operations in Next.js API Route Handlers authenticate users using the cookie-reliable `supabase.auth.getUser()`. To support multi-tenant team management, the system resolves the target scope by running `getEffectiveTenantId(user.id)`, which maps staff/agents to their account owner's `tenant_id` while returning the owner's own ID directly. Query operations are performed using a Supabase `service_role` client to bypass RLS, utilizing manual tenant-level filtering by this resolved `tenant_id`. API request bodies normalize camelCase and snake_case parameters (e.g. `templateId` and `template_id`) seamlessly to ensure robust client and schema alignment.
- **Light/Dark Mode & Theme Toggle**: Integrated light and dark theme styling using CSS variables. Default is light mode. Theme toggling is supported via a UI toggle button in the `Topbar.tsx` component which syncs selection to `localStorage`. An inline script in `layout.tsx` runs before paint to prevent theme flash (FOUC) by loading the correct class on the root element.

## Key Integration
- **Meta Embedded Signup, Auto-Registration, & Token Rotation**: Custom flow utilizing `NEXT_PUBLIC_META_CONFIG_ID`. Employs direct accessToken storage (`/api/whatsapp/store-token`) during `FB.login` and auto-discovers verified assets via `/api/whatsapp/connect` or `/api/whatsapp/sync-connection` using dual WABA/business lookup methods. Access tokens are immediately exchanged for 60-day long-lived tokens. Webhook app subscriptions are registered using a fallback/retry loop trying the global `META_SYSTEM_TOKEN` and user's access token sequentially. During initial setup, the phone number is automatically registered with Meta Cloud API using an auto-generated random 6-digit registration PIN stored in the `registration_pin` column on `wa_connections` table (added via migration `supabase/add_registration_pin.sql`). Manual or fallback phone registration via `/api/whatsapp/register-phone` dynamically reads the stored PIN, falling back to generate a random 6-digit PIN on the fly if needed (requiring zero user input). The registration API attempts registration using the system token first (admin privileges) before falling back to the user token, translating Meta registration failures (e.g. migration, duplicate registration) into user-actionable instructions. If registration fails because the number is active on personal WhatsApp, the Settings page displays a "Start Migration (OTP)" button initiating a migration flow (submitting code requests via `/api/whatsapp/request-verification-code` and verifying OTP via `/api/whatsapp/verify-code` to deactivate personal WhatsApp, register it, and poll the profile endpoint until activation completes). Settings page also offers a single-click "Register Phone Number Now" fallback. Validates manual Phone Number IDs on connection setup via `/api/whatsapp/validate-phone-id` to prevent WABA ID copy-paste errors, and provides a Troubleshooting panel on `/connect` page for manual overrides. The system automatically monitors and updates token lifecycles via a daily cron endpoint `/api/cron/refresh-tokens` for tokens expiring within 10 days, recording `token_expires_at` in the `wa_connections` database.
- **Campaign Wizard & Background Dispatcher (with QStash & Redis)**: Endpoints at `/api/campaigns` manage draft, scheduled, and immediate campaigns. Launching immediate or scheduled campaigns leverages Upstash Redis and QStash to execute batch dispatching (50 contacts per batch) asynchronously via `/api/campaigns/[id]/process-batch` route handler callback, bypassing Vercel timeout constraints and allowing auto-retries. Within each batch, message sending is processed in parallel using chunking (concurrency of 20) and `Promise.allSettled`, and subsequent database operations (updating conversations, message logs, and chat messages) are performed in parallel bulk writes for maximum efficiency. Redis cache manages query variables (with specific TTLs) and handles sliding-window rate limit checks (`checkMetaRateLimit` limit of 75 messages/sec per WABA phone number). A shared campaign runner utility `src/lib/campaign-sender.ts` manages segment processing, variable substitution, database logging, and inbox thread syncing. The batch dispatcher at `/api/campaigns/[id]/process-batch` dynamically parses and attaches template header parameter payloads for media assets (IMAGE, VIDEO, DOCUMENT) in addition to body text parameters. Upon campaign completion, the batch dispatcher resolves the tenant's email address and sends a detailed, beautifully styled HTML campaign performance report (Sent, Delivered, Read, Failed metrics) via Resend. A minute-by-minute worker cron at `/api/worker/campaigns` (secured via `CRON_SECRET`) picks up pending scheduled campaigns, flags them, and enqueues their batches, actively filtering out opted-out contacts (`opted_in = false`) at fetch time. The batch dispatcher at `/api/campaigns/[id]/process-batch` performs a redundant guard filtering out any contacts with `opted_in === false`, and automatically executes token fallback retries (retrying with the tenant's connection token if the system token fails with permission code 200 or 190, invalidating the Redis connection cache). If message dispatching fails, detailed Meta error details (code, subcode, trace ID) are serialized and recorded under the `error` column on the `message_logs` table (added via migration `supabase/add-message-logs-error-column.sql`). The template payload builder in `src/lib/meta.ts` and dispatch routes dynamically omit the `components` key if empty, preventing Meta API validation rejections for static templates without variables. Outbound template dispatches resolve and save the actual template body text (truncated to 120 chars) in conversation logs to provide meaningful message previews in the inbox. Delivery/read webhook status updates dynamically track stats, while failed webhooks increment failure counts and subtract from active sent counts. Detailed sandbox errors are logged to `message_logs`. Excluded batch routes from authentication middleware in `src/middleware.ts` to allow QStash callback triggers to bypass redirects.

- **Webhooks**: Automated status event handling at `/api/webhooks/meta` verifying payload signatures via HMAC SHA-256 using `META_APP_SECRET`. Parses incoming delivery updates, updates message status fields in both `chat_messages` and `message_logs` tables, records the `read_at` timestamp for read messages, and increments associated campaign delivery counts (`delivered_count`/`read_count`). Also processes incoming WhatsApp message types (text, interactive buttons, quick reply buttons, reactions, orders, image, audio, video, document), dynamically mapping incoming events to local threads using prefix-agnostic OR queries (matching both raw and `+` prefixed phone formats) to avoid duplicate conversation thread generation when customers reply.
- **Dynamic Analytics & Cross-Route Action Panel**: Unified analytics aggregation route `/api/analytics` fetches campaign delivery indices and chronological message logs, extending metrics to cover total delivered and failed logs, querying and grouping sent records strictly by `sent_at` (to prevent empty charts from `created_at` values which are null for batch actions) and read records by `read_at`. It parses `from` and `to` query parameters to retrieve log aggregates within a customizable date range (offering preset options of 7d, 14d, and 30d, or custom calendar limits selected via dropdown pickers). Both the detailed `/analytics` route and the main home dashboard page (`/`) fetch live metrics and charts dynamically based on these range selections. An onboarding checklist (`OnboardingChecklist.tsx`) on the home page dashboard tracks setup progress (WhatsApp connection, contacts import, template creation, campaign launch) based on real-time tenant stats, auto-dismissing when all tasks are done. Removed default mock data when chart records are empty so that analytics strictly reflect actual message counts from day one, with custom empty placeholder illustrations in `/analytics` dashboard views. Interactive triggers on the home dashboard wire action clicks to navigate seamlessly to deep nested page modal dialogs (Campaign Wizard, Import CSV drawer) via lightweight client URL hash filters.
